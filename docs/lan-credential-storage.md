# LAN credential storage

SubnetDesk authenticates the controlling device to the controlled device with a
LAN access **username and password**, configured on the controlled side
(`Settings → Network`). This document describes how the controlling side may
remember that password, and what it deliberately does not do.

## Where the password lives

| Platform | Backend | Entry name |
| --- | --- | --- |
| Windows / macOS / Linux | OS credential store through the `keyring` crate | service `com.zibochen.SubnetDesk.LANCredentials`, account `lan-credential-<device fingerprint>` |
| Android | Android Keystore (AES-256-GCM) through `SecureCredentialStore.kt` | shared preference `subnetdesk_secure_credentials`, key `<service>\|<account>` |
| iOS / Web | unsupported | — |

The username is not secret and stays in the peer config (`lan-access-username`).
Only the password goes to the platform store. `PeerConfig.password` is always
cleared, so no password is ever written to the JSON config files.

LAN **accounts** (identities, used by the desktop account manager) store their
password in the same backends under
`com.zibochen.SubnetDesk.LANIdentities` and the identity UUID.

## Android ciphertext format

`SecureCredentialStore` keeps one non-exportable AES-256 key in the
`AndroidKeyStore` under the alias `subnetdesk_lan_credentials_v1`
(`PURPOSE_ENCRYPT | PURPOSE_DECRYPT`, `BLOCK_MODE_GCM`,
`ENCRYPTION_PADDING_NONE`, 256 bit, randomized IV required).

Each stored value is `Base64(IV || ciphertext || GCM tag)` with a 12-byte IV and
a 128-bit tag. The IV is generated by `Cipher.init(ENCRYPT_MODE, key)` and stored
next to the ciphertext; the GCM tag is appended by `Cipher.doFinal`.

## Lifecycle

1. The user checks **Remember password** while entering LAN credentials.
2. The credential is submitted with `remember = true`, but nothing is persisted
   yet.
3. Only after the remote device accepts the login (`handle_peer_info`) does the
   core call `save_remembered_lan_credential`.
4. The next connection for the same device fingerprint loads the credential
   before showing any dialog.
5. A rejected password clears the stored credential and re-opens the dialog.
6. Connecting successfully with **Remember password** unchecked clears a
   previously stored credential.
7. The peer menu offers **Forget saved password** to delete it explicitly.

The remote device is identified by its TLS public-key fingerprint, so a
credential is bound to one device even when its IP address changes.

## Invariants

* The plaintext password never crosses into Dart. Rust reads it from the
  platform store, sends it, and zeroizes its buffers (`Zeroizing`,
  `LanSessionCredential: ZeroizeOnDrop`).
* There is no plaintext fallback. If the platform store is unavailable the
  "remember" request fails visibly and the connection continues without saving.
* Desktop entry names are unchanged, so credentials saved by earlier releases
  keep working without a migration step.

## Known limitations

* The JVM heap holds a plaintext `String` while encrypting or decrypting; it
  cannot be zeroized and is reclaimed by the garbage collector.
* The Android key is not bound to user authentication, so reconnecting does not
  prompt for a biometric or lock-screen check (the same trade-off as the desktop
  OS keyring).
* A backup restored onto another device cannot decrypt the blobs (the Keystore
  key is not part of the backup). The unreadable entry is deleted and the user is
  asked again.
* If a device is reinstalled and presents a new fingerprint, the credential
  saved for the old fingerprint is orphaned. It is not cleaned up automatically.
* Accounts (identities) are still managed from the desktop UI only; Android uses
  the per-device remembered credential.
